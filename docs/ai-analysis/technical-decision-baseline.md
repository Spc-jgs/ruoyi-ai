# AI 律师二开技术决策草案

> 版本：v1.0
> 基线：RuoYi-AI tag 3.0.0
> 日期：2026-05-08
> 用途：明确当前阶段不做的决策、先沿用的技术、后续需评估的技术点、建议技术路线

---

## 1. 当前阶段不做的技术决策

| 不做的事 | 原因 | 什么时候再评估 |
|---------|------|--------------|
| 不急着换向量库 | RuoYi-AI 已支持 Milvus/Weaviate/Qdrant 三种，默认 Milvus 可用 | 法律知识库数据量上来后评估是否需要换 |
| 不急着自研 RAG | RuoYi-AI 的 RAG 链路完整（上传→解析→切片→向量化→检索），先用现有能力 | 法律领域检索精度不足时评估自研或引入 Rerank |
| 不急着接腾讯 IM | IM 集成工作量大，一期用留言/意向提交替代 | M5 阶段 |
| 不急着做本地大模型部署 | Ollama Provider 已内置，但法律领域对精度要求高，先用云端模型 | M4 阶段评估 |
| 不急着做支付/分账 | 需要支付牌照、对账、退款、分账，复杂度极高 | M5 阶段 |
| 不急着重构 ChatServiceFacade | 603 行确实过重，但拆分风险极高，当前无业务压力 | M3 阶段评估 |
| 不急着做法律知识图谱 | Neo4j 在项目中已排除自动配置，知识图谱需求不明确 | M6 阶段 |
| 不急着做语音/视频咨询 | 技术栈不匹配，需要 WebRTC | M6 阶段 |

## 2. 当前阶段先沿用的技术

| 技术 | 沿用范围 | 说明 |
|------|---------|------|
| RuoYi-AI 认证权限 | `ruoyi-common-satoken` + `LoginHelper` + `@SaCheckPermission` | Sa-Token + JWT，成熟稳定，不要换 |
| RuoYi-AI 多租户 | `ruoyi-common-tenant` + `TenantEntity` + `tenant_id` | 数据隔离自动注入，不要换 |
| RuoYi-AI AI 对话链路 | `ChatServiceFacade` → `ChatServiceFactory` → Provider | 6 个 Provider 开箱即用，不要重构 |
| RuoYi-AI 知识库/RAG 链路 | `KnowledgeAttachServiceImpl` → `VectorStoreServiceImpl` | 上传→解析→切片→向量化→检索，完整可用 |
| RuoYi-AI 文件上传和 OSS | `ruoyi-common-oss` + `OssService`（MinIO） | 文件存取完整可用 |
| SSE 流式响应 | `ruoyi-common-sse` + `SseMessageUtils` | 流式推送协议完整，不要动 |
| MyBatis-Plus ORM | `ruoyi-common-mybatis` + `BaseMapperPlus` | CRUD 基础设施，不要换 |
| 审批工作流 | `ruoyi-workflow`（Warm-Flow） | 用于律师入驻审核、合同模板审核 |
| 代码生成器 | `ruoyi-generator`（Velocity） | 新模块 CRUD 脚手架 |

## 3. 后续需要评估的技术点

### 3.1 模型供应商

| 评估点 | 当前状态 | 待评估 |
|--------|---------|--------|
| DeepSeek | Provider 已有 | 法律领域回答质量如何？ |
| 通义千问 | Provider 已有 | 法律领域回答质量如何？ |
| 智谱 | Provider 已有 | 法律领域回答质量如何？ |
| OpenAI | Provider 已有 | 国内网络可访问性？ |
| Ollama | Provider 已有 | 本地部署法律模型？ |
| PPIO | Provider 已有 | 成本/质量？ |
| **法律专用模型** | 无 | 是否需要接入 ChatLaw/律政大模型等？ |

### 3.2 法律知识库来源

| 来源 | 可行性 | 评估点 |
|------|--------|--------|
| 购买法律数据库 | 中 | 成本、数据格式、更新频率 |
| 爬取公开法律文书 | 低 | 合规风险、数据质量 |
| 自建知识库 | 中 | 人力成本、覆盖面 |
| 对接第三方法律 API | 中 | 接口可用性、费用、数据完整性 |

### 3.3 Prompt 模板管理

| 评估点 | 说明 |
|--------|------|
| 当前状态 | system prompt 硬编码在 `ChatServiceFacade.buildContextMessages()` |
| 需要 | 法律领域需要不同场景的 Prompt（合同审查/案件分析/法规问答/风险评估） |
| 方案 | 新增 `prompt_template` 表 + 配置化加载，不修改 ChatServiceFacade |
| 时机 | M3 阶段 |

### 3.4 RAG Rerank

| 评估点 | 说明 |
|--------|------|
| 当前状态 | 纯向量检索，`ModelType.RERANKER` 已定义但未使用 |
| 需要 | 法律领域检索精度要求高，纯向量检索可能不够 |
| 方案 | 引入 Rerank 模型（bge-reranker 等），在 `VectorStoreService` 检索后增加 Rerank 层 |
| 时机 | M3 阶段，根据 RAG 实际效果决定 |

### 3.5 文档解析质量

| 评估点 | 说明 |
|--------|------|
| 当前状态 | Apache Tika 解析 doc/docx/pdf，基本可用 |
| 需要 | 法律文书格式复杂（合同/判决书/起诉状），解析精度可能不足 |
| 方案 | 评估是否需要定制化解析器（如合同关键条款提取） |
| 时机 | M3 阶段 |

### 3.6 法律回答合规免责声明

| 评估点 | 说明 |
|--------|------|
| 当前状态 | 无免责声明机制 |
| 需要 | **必须有**，AI 回答法律问题存在执业风险 |
| 方案 | 在 AI 回复后自动附加免责声明，或在对话界面固定展示 |
| 时机 | **M2 前必须确认** |

### 3.7 腾讯 IM 接入边界

| 评估点 | 说明 |
|--------|------|
| 当前状态 | 无 IM 能力 |
| 需要 | 律师与 C 端用户的实时沟通 |
| 方案 | 接入腾讯 IM SDK，或使用 WebSocket 自建 |
| 时机 | M5 阶段 |

### 3.8 支付订单和佣金分账

| 评估点 | 说明 |
|--------|------|
| 当前状态 | 无支付能力 |
| 需要 | 合同模板付费下载、律师服务付费 |
| 方案 | 微信支付/支付宝 + 分账（需要支付牌照或第三方服务商） |
| 时机 | M5 阶段 |

### 3.9 API Key 加密

| 评估点 | 说明 |
|--------|------|
| 当前状态 | `chat_model.api_key` 明文存储 |
| 需要 | 生产环境必须加密 |
| 方案 | 使用 MyBatis-Plus 的 `mybatis-encryptor`（已内置，`application.yml` L164-175 配置关闭状态） |
| 时机 | M4 阶段，上线前必须开启 |

### 3.10 数据权限隔离

| 评估点 | 说明 |
|--------|------|
| 当前状态 | RuoYi 支持部门级数据权限（`sys_role.dataScope`），但服务商维度不清晰 |
| 需要 | 服务商只能看自己管辖范围的数据 |
| 方案 | 评估是否需要自定义数据权限插件，或利用多租户能力 |
| 时机 | M5 阶段 |

## 4. 建议技术路线

### 阶段路线图

```
M0（当前）：跑通原项目
  ├── 本地启动 RuoYi-AI 后端
  ├── 启动必需中间件（MySQL/Redis/Milvus/MinIO）
  ├── 验证 AI 对话基础能力
  └── 验证管理端基础功能

M1：验证 AI 对话和知识库
  ├── 验证 SSE 流式响应链路
  ├── 验证知识库/RAG 全链路（上传→解析→切片→向量化→检索→回答）
  ├── 验证文件上传和 OSS
  ├── 验证多模型 Provider 切换
  └── 输出验证报告，记录发现的问题

M2：确认 MVP
  ├── 确认 AI 律师 MVP 范围（参考 ai-lawyer-secondary-development-baseline.md）
  ├── 确认免责声明方案
  ├── 确认律师入驻审核流程
  ├── 出详细 PRD 和数据库设计
  └── 确认新模块拆分方案

M3：新增 AI 律师业务模块
  ├── 新建 ruoyi-lawyer 模块（律师/律所信息管理）
  ├── 新建 ruoyi-legal-consult 模块（法律咨询/意向管理）
  ├── 新建 ruoyi-contract 模块（合同模板管理）
  ├── 新增管理端菜单（律师管理/合同管理/审核管理）
  ├── 配置律师入驻审核工作流
  └── 评估 Prompt 模板管理和 Rerank

M4：接入合同模板和律师入驻
  ├── 合同模板上传/审核/下载全流程
  ├── 律师入驻/审核/激活全流程
  ├── 律师 AI Agent 基础能力（案件分析/文书草拟）
  ├── 法律知识库建设和分类
  ├── API Key 加密开启
  └── 管理端完善

M5：再考虑订单、IM、佣金
  ├── 接入支付（微信/支付宝）
  ├── 接入腾讯 IM（律师-C端沟通）
  ├── 律所抽佣和分账
  ├── 服务商数据平台
  └── 数据权限隔离
```

### 技术决策原则

1. **先复用后新建**：RuoYi-AI 已有的能力直接用，不重复造轮子
2. **先验证后开发**：M0/M1 验证链路可用后再设计业务
3. **先新增后重构**：新业务模块独立新增，不污染核心链路
4. **先免费后付费**：合同模板先免费，验证需求后再做付费
5. **先基础后高级**：AI 对话先用通用模型 + RAG，验证不够再引入法律专用模型
